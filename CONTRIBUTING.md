# Как работать над проектом

Документ фиксирует правила из инструкции по оформлению кода и проверкам.
**Главный принцип: если правило нельзя проверить линтером, тестом или CI —
оно будет нарушаться.** Поэтому каждое правило ниже имеет механизм проверки.

Перед написанием кода, во время и после — сверяйтесь с этим файлом,
`STYLEGUIDE.md` и `ERRORS.md`.

---

## 1. Обязательный цикл работы

```
1. Проверить ERRORS.md — возможно, ошибка уже описана
2. Написать регрессионный тест (если это исправление бага)
3. Написать код
4. make check  →  ruff + mypy + pytest
5. Обновить CHANGELOG.md (если изменение видит пользователь)
6. Обновить ERRORS.md (если исправлен баг)
7. Коммит по Conventional Commits
8. PR по шаблону .github/pull_request_template.md
```

Пункты 1, 6 и 7 — не формальность: именно они не дают второй раз
разбираться с одной и той же ошибкой наугад.

---

## 2. Локальные проверки

Всё, что делает CI, должно запускаться локально одной командой:

```bash
make check       # форматирование + линтер + типы + тесты
make test        # только тесты
make lint        # только ruff
make types       # только mypy
make fix         # автоформатирование и автоисправления
```

Без `make` (Windows):

```bat
ruff format src tests
ruff check src tests --fix
mypy src
pytest
```

**Нельзя мержить «на глаз»**: если локально `make check` не проходит,
CI тоже будет красным.

---

## 3. Quality gates (что проверяет CI)

PR не проходит, если не выполнено хоть одно:

| Проверка | Инструмент | Где настроено |
|---|---|---|
| Форматирование | `ruff format --check` | `.github/workflows/ci.yml` |
| Линтер | `ruff check` | `pyproject.toml [tool.ruff]` |
| Типы | `mypy` | `pyproject.toml [tool.mypy]` |
| Unit-тесты | `pytest` | `tests/` |
| Покрытие | `pytest --cov` | `pyproject.toml [tool.coverage]` |
| Сборка артефакта | `python -m build` | CI, шаг build |
| Уязвимости зависимостей | `pip-audit` | CI |
| Секреты в коде | `gitleaks` | CI |
| Конфигурация | `python -m tvhost.proxy --selftest` | CI |

Список синхронизирован с разделом 8 инструкции.

## 4. Разделение слоёв

Код разложен по слоям; **нарушение направления зависимостей — ошибка**:

```
src/tvhost/
├── core/        бизнес-логика: закрепление ссылок, загрузка. Без UI и сети-напрямую
├── infra/       доступ к внешнему миру: сеть, ffmpeg, кеш, диагностика, сайты
├── web/         страница-плеер (HTML/JS/CSS) — представление для телевизора
├── ui/          панель PySide6 — представление для ПК
├── proxy.py     транспорт: HTTP-сервер и маршруты
└── server.py    транспорт: альтернативный сервер
```

Правила:
- `core` **не импортирует** `ui`, `web`, `proxy`;
- `infra` не импортирует `ui`;
- `ui` не содержит бизнес-логики — только отображение и вызовы;
- HTTP-маршруты живут в `proxy.py`, их обработчики — по одному методу на маршрут.

Smoke-проверка слоёв: `pytest tests/test_architecture.py`.

## 5. Правила кода

Кратко (подробно — `STYLEGUIDE.md`):

- функция ≤ 40 строк, вложенность ≤ 4;
- цикломатическая сложность ≤ 15 — проверяет `ruff` (`C901`);
- никаких «магических» чисел — в константы с именем;
- никаких `print` вне точек входа — проверяет `ruff` (`T201`);
- никаких закомментированных блоков — проверяет `ruff` (`ERA`);
- никаких `except: pass` без объяснения в комментарии — проверяет `ruff` (`S110`);
- публичные функции и классы — с docstring, объясняющим **почему**, а не что;
- ошибки не глотать: добавлять контекст при пробросе.

## 6. Тесты

Обязательный минимум для каждого изменения:

| Что изменилось | Что нужно |
|---|---|
| Новая функция ядра | unit-тест: happy path + границы + негативный случай |
| Исправлен баг | регрессионный тест, который падает без исправления |
| Новый маршрут HTTP | тест в `tests/test_routes.py` |
| Изменение страницы плеера | тест в `tests/test_player.py` (в т.ч. ES5-совместимость) |
| Новый внешний сайт | контрактный тест в `tests/test_sources_contract.py` |
| Изменение формата отчёта | тест в `tests/test_diagnostics.py` |

Требования к тестам:
- unit-тесты **без сети, без времени, без рандома** — иначе flaky;
- сетевые тесты — маркер `@pytest.mark.network`, запускаются отдельно;
- тест читается как требование: имя = что проверяется;
- в тесте одно утверждение-смысл, а не десять подряд.

### Покрытие

Ориентир из инструкции — 80%, **догмой не является**. Порог в
`pyproject.toml` — **12%** и может только расти:

```
12% (сейчас) → 25% → 40% → 60%
```

Порог поднимается отдельным PR, когда добавлены тесты. **Снижать
порог запрещено** — это обнуляет смысл проверки.

Критичные модули (должны быть покрыты в первую очередь):
`core/pins.py`, `infra/diagnostics.py`, `proxy.py` (маршруты), `web/player.py`.

## 7. Коммиты и ветки

Conventional Commits:

```
feat(proxy): разбить do_GET на таблицу маршрутов
fix(pins): расширение файла брать из пути, а не из параметров
test(diag): покрыть восстановление журнала из файла
docs(errors): добавить ERR-042 — порядок маршрутов
refactor(player): вынести настройки hls.js в константы
```

Ветки: `main` защищена. Работа — в `fix/…`, `feat/…`, `docs/…`.
Force-push в `main` и релизные ветки запрещён.

---

## 8. PR

- Размер — до 300–400 строк изменений; больше — дробить.
- Заполненный шаблон: что, зачем, как проверено, риски, откат.
- Минимум одно одобрение. Self-merge без исключения запрещён.
- «Красный» CI, конфликты и незакрытые блокирующие комментарии — не мержим.

---

## 9. Документация

Обновляется вместе с кодом, в том же PR:

| Изменилось | Обновите |
|---|---|
| Поведение для пользователя | `CHANGELOG.md` |
| Исправлена ошибка | `ERRORS.md` (новая запись `ERR-NNN`) |
| Архитектурное решение | `docs/adr/NNNN-название.md` |
| Новый маршрут/параметр | `README.md`, раздел «Маршруты сервера» |
| Новый сайт-источник | `README.md` + `ERRORS.md` |

---

## 10. Definition of Done

Задача выполнена, только если:

- [ ] код соответствует `STYLEGUIDE.md`, `ruff` и `mypy` зелёные;
- [ ] есть тесты на новое поведение; для бага — регрессионный;
- [ ] `make check` проходит локально, CI зелёный;
- [ ] ревью выполнено;
- [ ] `CHANGELOG.md` обновлён (если видит пользователь);
- [ ] `ERRORS.md` обновлён (если исправлен баг);
- [ ] нет новых критичных уязвимостей и секретов;
- [ ] понятен план отката;
- [ ] проверена работа на реальном сценарии (видео играет в браузере).

---

## 11. Чего не делать

- Не откатывать оформление, чтобы «починить» воспроизведение: причина
  всегда в данных или таймаутах (см. `ERRORS.md`, ERR-001).
- Не добавлять зависимости без обоснования в PR.
- Не оставлять `TODO` без номера задачи.
- Не хранить секреты и подписанные ссылки в коде, логах и отчётах.
- Не логировать в цикле «на каждый чих» — только значимые события.
