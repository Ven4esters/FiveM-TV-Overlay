## Почему `python3` не нашёлся

Python у вас **есть** — `python --version` показывает `Python 3.12.8`.
Не сработало вот что: в Windows команда установщика называется `python`,
а `python3` — это ярлык-заглушка из Microsoft Store. Она есть всегда, но
настоящий Python по ней не запускается, и выходит сообщение
«Python was not found; run without arguments to install from the Microsoft
Store». Настоящий Python при этом жив — просто зовут его иначе.

Правило простое: **в Windows — `python` (без цифры 3), в Linux — `python3`.**
Это моя ошибка в инструкции, я писал под Linux.

## Что запустить (два шага)

Ошибка `ModuleNotFoundError: No module named 'tvhost2'` — это уже не про
Python, а про то, что пакет лежит в подпапке `src\` и в системный Python не
установлен. Поэтому `python -m tvhost2.alloha_check` его не видит. Ставить
пакет не надо: в проекте и так есть окружение `.venv`, которое `start.bat`
создал при первом запуске.

### Шаг 1 — обновиться

В папке проекта:

```
git pull
```

Должна появиться строка **`93f8578 fix(alloha): check_alloha.bat`** или новее
(`git log --oneline -1`).

### Шаг 2 — двойной щелчок по `check_alloha.bat`

Он появился в папке проекта после `git pull`. Щёлкните дважды — спросит
ссылку, вставьте её и нажмите Enter.

Либо сразу с ссылкой, из консоли:

```
check_alloha.bat "https://zlord.org/25672-xorosaia-doc.html"
```

Почему именно он: батник берёт `.venv\Scripts\python.exe` и ставит
`PYTHONPATH=src` — ровно так, как это делает `start.bat`. Ничего
устанавливать и настраивать не нужно, окно приложения закрывать не надо
(команда только читает).

### Что покажет

| Строка в выводе | Что значит |
|---|---|
| `встройка: …` | нашлась встройка Alloha — ссылка правильная |
| `озвучек: 8` и список | открытый API ответил, озвучки есть |

В конце печатается путь к отчёту: `alloha_check\<дата>_summary.txt`.

### Что прислать мне

Один файл — этот `summary.txt`. Если было `ПОЛУЧЕНО` — ещё `<дата>_hlsSource.json`.

## Третий запуск (после `3a3c3c9`)

```
git pull
check_alloha.bat "https://zlord.org/25672-xorosaia-doc.html"
```

Что нового: шаг 3 теперь печатает **каждую** попытку отдельной строкой —
с каким номером файла, какой код ответа и есть ли в ответе `hlsSource`.
Раньше показывалась только последняя, и по ней нельзя было отличить «не тот
номер» от «не пускают».

Так это будет выглядеть (пример с провалом):

```
── 3. Запрос адресов (POST /bnsi)
попыток: 6 (по одной на номер файла)
   id 1836882 → 404 (hlsSource: нет)
   id 1847894 → 404 (hlsSource: нет)
   ...
```

Смотреть надо на первую строку: если **правильный** номер (первый в списке —
это `active.id`) тоже даёт 404, то номер файла тут больше ни при чём, и
дальше причина только в том, что Alloha требует чего-то ещё. Тогда по
списку будет видно, с какого номера начинается перебор, и это сузит поиск.

## Четвёртый запуск (после `bb1476d`)

Третий отчёт сделал своё дело: **номер файла ни при чём** — перебор начинался
с правильного `1847894`, и все шесть номеров дали один и тот же ответ
«контент не найден». Значит, дело в самом запросе. Тут я нашёл ошибку у себя:
плеер шлёт данные **формой** (`application/x-www-form-urlencoded`, так работает
jQuery), а мой пробник слал JSON. Теперь и приложение, и пробник шлют форму.

Чтобы не гадать по одному варианту за запуск, четвёртый прогон за один раз
проверяет сразу 12 вариантов запроса (по два номера файла на каждый):

- форма и JSON;
- `av1`: 0, 1, `true`;
- `autoplay`: 0 и 1;
- `Borth` с отпечатком, без отпечатка, без `Borth`;
- лишние поля `audio`, `subtitle`, `_ref`;
- без `X-Requested-With`;
- JSON с одним только `token`.

```
git pull
check_alloha.bat "https://zlord.org/25672-xorosaia-doc.html"
```

Если сработает хоть один — в окне появится строка «← ЕСТЬ hlsSource!» и
название варианта, а ответ сохранится в файл `..._variant_<имя>.json`.
**Пришлите summary.txt и этот json** — по названию варианта я закреплю
рабочий формат в приложении.

Если не сработает ни один — в отчёте будет 24 строки, все с одинаковым кодом.
Тогда остаётся один честный путь: снять настоящий запрос в браузере на вашем
ПК (Network → ПКМ по `bnsi` → Copy as cURL) и повторить его один в один.

## Седьмой запуск: что дал шестой (после `018592f`)

Шестой прогон отработал как надо: `curl.txt` разобрался (ошибка «адрес не
найден» ушла) и шаг 3б нашёл в странице плеера настоящий `refToken`:

```
форма, _ref=s1.1795638751.…   id 1847894 → 404
форма, _ref=s1.1795638751.…   id 1831135 → 404
```

Подпись сервер выдаёт и обновляет (время в ней новое), но адреса с ней
всё равно нет. Значит, `_ref` — не то, чего не хватало.

Я проверил снаружи всё, что оставалось непроверенным, и вот итог:

| Проверка | Результат |
|---|---|
| HTTP/2 настоящим клиентом (h2), браузерные заголовки, рабочий `_ref` | 404, те же 450 байт |
| HTTP/1.1 с UA браузера и поддельным `_ref` | 404 |
| Хост `tories.as.newplayjj.com:444` (он стоит на сайте) | 404 и на странице, и на `/bnsi` |
| `_ref` от нашего домена против домена заказчика | 404 в обоих случаях |

Из ваших HAR-файлов видно ещё одно: манифесты идут с `userplay.live` и
несут заголовки `Accepts-Controls` и `Authorizations: Bearer …` — это
те самые токены гарда. Их мы добывать умеем (`/sarn` + `/vorf`), но к
`/bnsi` они отношения не имеют: это проверено.

**Что теперь в приложении.** Раз плеер шлёт `_ref` всегда, приложение
теперь тоже: `form_payload()` собирает тело ровно как плеер, и подпись
попадает в боевой запрос, когда сервер её дал. На ответ это пока не
влияет, но наш запрос стал ближе к настоящему.

**Главное, что видно из отчётов.** Наш код берёт встройку из открытого
API Alloha (`tories-as.stravers.live/?token_movie=…`), а на сайте
zlord.org стоит другая (`tories.as.newplayjj.com:444/?kp=…`). Обе снаружи
России отвечают «контент не найден», так что сравнить их честно я не могу.

Дальше нужен ваш шаг — он же и последний в этой серии:

1. `git pull`
2. Открыть страницу с видео, дождаться, пока плеер начнёт играть.
3. `F12` → **Network** → фильтр `bnsi`.
4. Правой кнопкой по запросу → **Copy as cURL** → в `alloha_check\curl.txt`.
5. `replay_alloha.bat` — и прислать, что он напечатает.

Теперь разбор правильный, поэтому впервые будет видно, что отвечает
**дословно тот же** запрос, что в браузере: `hlsSource` или тот же 404.
От этого зависит следующий шаг — и он уже не про формат запроса.

## Шестой запуск: `_ref` и правильный разбор curl (после `7030aba`)

Пятый прогон дал две вещи: отчёт `check_alloha.bat` (шаг 3в отработал) и
скриншот `replay_alloha.bat` с «адрес: НЕ НАЙДЕН».

**Что было на скриншоте.** `curl.txt` сохранён в варианте Chrome
«Copy as cURL (cmd)». В нём cmd экранирует `^` всё особенное: кавычки
(`^"`) и амперсанды (`^&`). Разбор этого не снимал, поэтому адрес остался
`^https://…^`, имена заголовков — `^accept`, а тело — `token=…^&av1=true^&…`.
Исправлено: `^` снимается во всех полях, плюс прощаются BOM (его ставит
Notepad++) и «умные» кавычки из Word. Если команда совсем побита, адрес
достаётся регуляркой, а если и это не вышло — восстанавливается по
`Referer`.

**Что нового про сам запрос.** В теле, которое вы прислали, был `_ref`:

```
_ref=s1.1795636688_b9b59a5200accf9ca738b61c.aHR0cHM6Ly96bG9yZC5vcmc
        время      24 hex (подпись)          base64 = https://zlord.org
```

В расшифровке плеера это поле появляется только если сервер положил в
страницу `refToken`:

```js
userParam['refToken'] && (hf['_ref'] = userParam['refToken'])
```

Мы же всегда слали `_ref` пустым. Теперь шаг 3б берёт `refToken`
из страницы плеера (и из вашего `curl.txt`, если он лежит) и пробует
с ним. Подпись `24 hex` — серверный секрет: она не считается ни из
страницы, ни из времени, ни из токена, поэтому придумать её у себя
нельзя, а вот взять готовой — можно.

В образце страницы от 24.11.2026 `refToken` пустой, поэтому вариант
не появится, пока сервер его не даст. Если после обновления в шаге 3б
появилась строка `форма, _ref=s1.…` — значит, сервер его дал, и есть
шанс, что `/bnsi` ответит иначе.

**Что запустить:** `git pull`, затем `replay_alloha.bat` (он теперь
разберёт ваш `curl.txt` правильно), затем `check_alloha.bat` с той же
ссылкой.

## Пятый запуск: повтор запроса из браузера (после `6d90857`)

Четвёртый прогон отработал честно: 24 варианта запроса — и все 404. Это
закрыло последнюю версию, которая была «на нашей стороне» (тело и заголовки).
Дальше угадывать бессмысленно: в браузере запрос работает, у нас — нет, и
разницу видно только если сравнить два запроса буквально.

Поэтому теперь два инструмента за один заход.

**Шаг 1 — обновиться:**

```
git pull
```

> Если при запуске `check_alloha.bat` появилось «Не нахожу окружение проекта:
> .venv» — обновитесь и запустите снова. Диагностике окружение не нужно:
> она работает на обычном Python 3.10+, который у вас уже стоит (3.12.8).
> Проверено: все нужные файлы обходятся стандартной библиотекой.
>
> Отдельно ничего запускать не надо. Но если хотите, чтобы работало и само
> приложение: `start.bat` пересоздаст `.venv`. Это займёт пару минут и
> скачает зависимости.

**Шаг 2 — снять настоящий запрос плеера:**

1. Откройте страницу с видео и дождитесь, пока плеер начнёт играть.
2. F12 → вкладка **Network** (Сеть) → в фильтре наберите `bnsi`.
3. Правой кнопкой по строке `bnsi` → **Copy** → **Copy as cURL**.
4. Откройте Блокнот, вставьте, сохраните файл как
   `alloha_check\curl.txt` (в папке проекта уже есть папка `alloha_check`).
5. Двойной щелчок по **`replay_alloha.bat`**.

Он разберёт запрос (и однострочный, и многострочный — как бы браузер ни
скопировал), повторит его один в один и напечатает таблицу:

* какие заголовки браузер шлёт, а мы нет;
* сколько символов в `Borth` у браузера;
* что ответил сервер на **точно такой** запрос.

**Шаг 3 — тот же `check_alloha.bat`**, что и раньше. В нём появился новый
шаг **3в**: `Borth` с отпечатком, который считает сам сервер. Раньше
отпечаток собирался из выдуманных чисел (я так думал по расшифровке), а
теперь известно точно: сервер на `/sarn` отдаёт `uap` — это ровно
`sha256(User-Agent)`, и он же, судя по всему, и есть первая половина `Borth`.

Пришлите из `alloha_check`:

* `replay_curl_body.txt` — что ответило на браузерный запрос;
* `*_summary.txt` — отчёт `check_alloha.bat`.

Если браузерный запрос играет, а наш нет — по таблице будет видно, чего не
хватает. Если и браузерный повтор даёт 404 — значит, дело не в самом
запросе, а в том, чем он отправлен, и тогда следующий шаг будет другой.

## Что уже исключено (проверено мной снаружи России)

Чтобы вы не гоняли одно и то же:

| Версия | Проверка | Итог |
|---|---|---|
| Неверный id | ваш второй отчёт: перебор начинается с 1847894 (TVShows) | **исключено** |
| Регион | страница плеера у вас пришла (14 202 байта, мета есть) | **исключено** |
| Cookies/сессия | сервер не ставит `Set-Cookie` даже на страницу | **исключено** |
| guard-токен (`Authorizations`) | он нужен для CDN-манифеста, не для `/bnsi` | **исключено** |
| Зеркала плеера | 4 домена, снаружи все отвечают одинаково | **исключено** |
| Неверная озвучка в адресе | API сам отдаёт этот iframe для серии 1 | **исключено** |
| Не тот номер файла | 3-й отчёт: перебор с правильного `1847894`, все 6 → 404 | **исключено** |
| JSON вместо формы | плеер шлёт форму — теперь шлём форму первой | **проверено, было ошибкой у меня** |
| Тело и заголовки запроса | 4-й отчёт: 24 варианта — все 404 | **исключено** |
| Отпечаток Borth из выдуманных чисел | сервер отдаёт `uap` = `sha256(UA)`; берём его (шаг 3в) | **проверено, было слабым местом** |
