## ERR-069 — Rutube: видео «есть», но поток не отдаётся (правообладатель)

**Дата:** 23.11.2026
**Ссылка-воспроизведение:** `https://rutube.ru/video/e1c3757f9a3db09a224ac95c836cecbf/`

**Симптом.** yt-dlp падает с `HTTP Error 404`, хотя страница открывается.

**Разбор.**
| Запрос | Ответ |
|---|---|
| `GET /video/<hash>/` (страница) | 200, HTML |
| `GET /api/video/<hash>/` (метаданные) | 200 — «Супермен \| Superman (2025)» |
| `GET /api/play/options/<hash>/` | **отказ**: `blocking_rule` |

**Причина.** Правообладатель ограничил показ за пределами РФ. Из
песочницы (IP США/за рубежом) поток недоступен. Видео при этом живое:
из России откроется.

**Решение.** Отдельный тип ошибки `RightsBlockedError`:
- НЕ помечает источник «сломан» (`state=OK`);
- в интерфейсе говорит «правообладатель ограничил показ», а не «ошибка»;
- не тратит повторный запрос на embed — запрет он не обойдёт.

**Урок.** «404» ≠ «видео нет». Для Rutube это чаще «скрыто от этого IP».
Проверять `blocking_rule` в ответе API до того, как отдавать пользователю
слово «ошибка».

## ERR-070 — `sorted(list_extractors())` падает с TypeError

**Симптом.** `AttributeError: 'TenPlayIE' object has no attribute '__name__'`.

**Причина.** `yt_dlp.extractor.list_extractors()` возвращает **экземпляры**
классов, а не строки. Часть экземпляров обращается к атрибутам, которых
у класса нет.

**Решение.** `type(obj).__name__` для каждого элемента, `sorted(key=str)`.

## ERR-071 — Kodik: прямая ссылка на плеер показывает «страницы не существует»

**Дата:** 23.11.2026
**Ссылка:** `https://kodikplayer.com/seria/1420137/746cbbd95c6ac9b2bd8c113953f63646/720p`

**Симптом.** Открытое напрямую окно показывает «Извините, но данной
страницы не существует». В iframe — работает.

**Причина.** В JS плеера:
```js
if (!isIframe() && location.hostname !== "localhost") { …подмена… }
```

**Решение.** Открывать через локальный iframe-обёртку (или через
`location.hostname = localhost`-подмену). Это же снимает вопрос
Referer-проверки.

**Найденный поток:** `https://p12.solodcdn.com/s/m/<base64>/<подпись>:<срок>/360.mp4:hls:manifest.m3u8`.
Подпись живёт ~сутки → кэш 12 часов.

## ERR-069 (дополнение) — как отличить блокировку от поломки

**Проверено на двух ссылках заказчика (23.11.2026):**

| Видео | Что сказал Rutube | Разрешено в |
|---|---|---|
| Супермен (2025) | `blocking_rule` | только РФ и СНГ |
| Гарри Поттер (2001) | `blocking_rule` + текст «…или у вас включён VPN» | **32 страны из ~250** |

**Точный способ проверки — до попытки воспроизведения:**

```http
GET https://rutube.ru/api/video/<hash>/
→ 200, в теле:
   "restrictions": {"country": {
       "allowed":    ["RU", "BY", "KZ", ...],   # где смотреть можно
       "restricted": ["US", "DE", "GB", ...]    # где нельзя
   }}
```

**Что это даёт.** Вместо «не удалось получить видео» можно сказать
человеку точно: «это видео доступно в 32 странах, ваша не входит».
Или наоборот — «у вас должно работать, дело в чём-то другом».

**Правило.** Для Rutube `blocking_rule` и `404` на
`/api/play/options/` — это **не** поломка источника.
Источник остаётся 🟢; недоступно конкретное видео с конкретного IP.

**Инструмент для заказчика:** `check_link.bat` —
запускается на его компьютере и проверяет ссылку с его IP,
то есть из страны, где видео может быть разрешено.

## ERR-072 — VK называет качество не тем, что отдаёт

**Дата:** 23.11.2026
**Ссылка:** `https://vkvideo.ru/video-220020068_456260705`

**Симптом.** В форматах VK есть `url1080`, но кадр у него — `1920x960`,
а не `1920x1080`. Подпись в интерфейсе получилась «960p» — качество,
которого человек не искал.

**Настоящая таблица VK (замеры 23.11.2026):**

| VK называет | Реальный кадр |
|---|---|
| 144p | 256x128 |
| 240p | 426x212 |
| 360p | 640x320 |
| 480p | 852x426 |
| 720p | 1280x640 |
| 1080p | **1920x960** |

**Причина.** Фильм 2:1 с чёрными полосами; VK обрезает кадр по высоте.
Название качества — «потолок», а не точный размер.

**Решение.** В `Quality` добавлено поле `nominal_height`:
- `label` показывает паспортное «1080p» (человек ищет именно его);
- `height` остаётся настоящим 960 (нужно для `RESOLUTION` в мастере);
- для незнакомого кадра `nominal=0` — тогда подпись честно по факту.

**Урок.** Никогда не выводить подпись качества из «сырых» размеров кадра.
Сайт знает, как он сам называет свои качества, — надо спрашивать у него.

## ERR-073 — у вертикального видео качество меряется по ШИРИНЕ

**Симптом.** Клип `1080x1920` подписывался «1920p» и вставал в списке
выше 4K.

**Причина.** Общая формула «качество = высота» верна для горизонтального
видео и ломается для вертикального.

**Решение.** Для `is_portrait` подпись — `1080x1920 (верт.)`: видны обе
стороны, и сразу понятно, что видео вертикальное.

**Урок.** «Качество» — это не одно число. Нужны и ширина, и высота,
и понимание ориентации (см. ERR-062 — первая встреча с этим в v1).

## ERR-074 — YouTube: звук не в HLS, а склейка обязательна

**Дата:** 23.11.2026
**Ссылки:** `watch?v=aqz-KE-bpKQ` (VOD), `watch?v=xbeH0wcBwjw` (live)

**Что показали замеры:**

| Дорожка | Тип | Что внутри |
|---|---|---|
| 269…270 (H.264) | HLS-плейлист | видео **без звука** |
| 233, 234 (аудио) | HLS-плейлист | сегменты — **сырые AAC** (`ID3` в начале) |
| 140, 251 (аудио) | прямой mp4/webm | файл целиком |
| мультиплекс | — | **нет вообще** (ни в VOD, ни в live) |

**Почему нельзя собрать master-плейлист.** hls.js в группе
`EXT-X-MEDIA:TYPE=AUDIO` ждёт MPEG-TS или fMP4-сегменты. YouTube отдаёт
сырой AAC — такой поток браузер не проиграет: получится видео без звука.

**Решение.** Склеивать на своей стороне:
```
ffmpeg -i <видео-HLS> -i <аудио-HLS> -c copy -movflags +faststart out.mp4
```
`-c copy` — без перекодирования, поэтому быстро: **10:34 видео 720p
склеены за 25 секунд**, на выходе h264 + AAC 1280x720, 154 МБ.

Цена: ffmpeg должен быть на компьютере. На Windows — `imageio-ffmpeg`
(в нём уже лежит готовый бинарник).

**Урок.** «Отдать плейлист» и «сделать так, чтобы заиграло» — разные задачи.
Проверять надо второе: скачать и посмотреть, есть ли в файле обе дорожки.

## ERR-075 — YouTube: VP9 и AV1 браузер игры не воспроизводит

**Симптом.** Если взять «лучший» формат по битрейту, приходит VP9
(`vp09.00.40`) или AV1 (`av01.0.09M`) — в CEF внутри GTA 5 чёрный экран.

**Решение.** Отбирать только `vcodec.startswith("avc1")` (H.264).
Если H.264 нет совсем — честно отдавать ошибку, а не «работающий» поток,
который не играет.

**Урок.** «Максимальное качество» ≠ «то, что заиграет». Сначала кодек,
потом битрейт.

## ERR-076 — Я сделал неверный вывод по спецификации вместо эксперимента

**Дата:** 23.11.2026
**Кто поймал:** заказчик. «У меня вполне работают и прямые ссылки на YouTube
со звуком в игровом телевизоре».

**Что я утверждал.** Что hls.js не проиграет сырой AAC-сегмент YouTube
(itag 233) в аудиогруппе `EXT-X-MEDIA`, потому что сегмент не MPEG-TS,
а начинается с `ID3`. Отсюда «единственный путь — склейка ffmpeg».

**Что оказалось на самом деле.** hls.js это проигрывает. Замер в реальном
Chromium (`webkitAudioDecodedByteCount` — счётчик ДЕКОДИРОВАННОГО звука):

| Момент | readyState | Время | Аудио, байт | Видео, байт | Кадр |
|---|---|---|---|---|---|
| старт+10с | 4 | 8.8 | 56 508 | 2 257 392 | 1920x1080 |
| +8с | 4 | 16.8 | 105 603 | 8 917 911 | 1920x1080 |
| seek 2:05 | 4 | 125.3 | 140 718 | 12 610 178 | 1920x1080 |
| смена 480p | 4 | 132.3 | 183 436 | 12 710 454 | 640x360 |
| финал | 4 | 142.3 | 245 286 | 12 885 093 | 640x360 |

Звук декодируется, перемотка работает, ручная смена качества работает.
Единственные ошибки — `warn bufferFullError`, то есть буфер ПОЛОН
(«слишком хорошо»), а не пуст.

**Стоимость ошибки.** Я успел написать склейку через ffmpeg: 25 секунд
ожидания на старте, 150 МБ на диске, сотни МБ ОЗУ. На компьютере
заказчика с 8 ГБ ОЗУ это неподъёмно. Правильный путь — прямой мастер
через прокси: старт 1–2 с, ноль диска, ABR на лету.

**Правило, которое теперь соблюдаю.**
> Библиотека «по спецификации» и библиотека «на деле» — разные вещи.
> Прежде чем строить обходной путь, запустить минимальный эксперимент
> и измерить результат, а не рассуждать о нём.

Метрика, которая не обманывает: `webkitAudioDecodedByteCount` — если
растёт, звук действительно декодируется (а не просто «загрузился»).

**Инструмент остался в проекте:** `tests/manual/probe_hls_audio.py` —
проверяет любой HLS-мастер на реальное декодирование звука.

## ERR-077 — Twitch: клипы приходят без кодеков

**Дата:** 23.11.2026
**Ссылка:** `twitch.tv/riotgames/clip/ObservantKawaiiCockroachPogChamp`

**Симптом.** Клип разобрался, но качеств — ноль, приложение сказало
«Twitch не отдал ни одного качества».

**Причина.** У клипов yt-dlp НЕ заполняет `vcodec` и `acodec` (для VOD и

**Урок.** «Нет поля» ≠ «нет данных». Разные типы одной ссылки могут
заполняться по-разному — проверять на всех трёх (стрим / запись / клип).

## ERR-079 — Kodik вскрыт полностью (шифр, API, озвучки)

**Дата:** 23.11.2026
**Ссылка:** `kodikplayer.com/seria/1420137/746cbbd95c6ac9b2bd8c113953f63646/720p`

**Было:** «нужна браузерная сессия, ~20 секунд на разбор, непонятно откуда
ссылки».

**Стало:** обычный HTTP, 1.3 секунды, без Chromium вообще.

### Схема

```
GET  /seria/<id>/<hash>/720p
     → HTML, в нём подписи:
       var domain, d_sign, pd, pd_sign, ref, ref_sign
     → и ВСЕ озвучки как <option data-media-hash="...">
       (у каждой свой hash → свой поток)

POST /ftor   (x-www-form-urlencoded)
     d, d_sign, pd, pd_sign, ref, ref_sign,
     bad_user=false, cdn_is_working=false,
     type=seria, hash=<hash>, id=<id>, info={}
     → JSON: {"links": {"360": [{"src": "<шифр>"}], "480": [...], "720": [...]}}
```

### Шифр ссылки (разгадан)

Двойное кодирование, в обратном порядке:
1. **ROT18** — сдвиг латинских букв на 18 (цифры/знаки не трогаются);
2. **base64** — декодировать.

```python
decoded = base64.b64decode(rot18(encoded)).decode("latin-1")
# → https://p12.solodcdn.com/s/m/.../720.mp4:hls:manifest.m3u8
```

**Важно:** ROT18 НЕ симметричен сам себе (18+18 = сдвиг на 10).
Обратный сдвиг — ROT8. Ошибка в этом ломает всё разом.

### Проверка, что видео ИГРАЕТ (не только «ссылки есть»)

| Проверка | Результат |
|---|---|
| Озвучек найдено | 6 (AniDUB, AniStar, AnimeVost, LightFamily, СВ-Дубль, субтитры) |
| Озвучек отдало поток | **6 из 6** |
| Качеств в каждой | 720p, 480p, 360p |
| Время на одну озвучку | ~1.1 с |
| Реальный поток 720p | `h264 High 1280x720` + `aac LC 44100 stereo` |
| Скачано за 32 с | 60 секунд видео, 8.4 МБ, обе дорожки |

**Урок.** «Получил ссылки» ≠ «видео играет». Скачивать 60 секунд через
ffmpeg и смотреть, есть ли ОБЕ дорожки — единственный честный тест.

## ERR-080 — Громкость: разброс 19 дБ между источниками

**Дата:** 23.11.2026
**Жалоба заказчика:** «регулировка звука, иногда даже на маленьких значениях,
выдаёт громкий звук. Полагаю это связано с источником».

**Догадка заказчика верна.** Замер EBU R128 на живых потоках:

| Источник | Громкость | LRA | Пик |
|---|---|---|---|
| Rutube (своя загрузка) | **-39.9 LUFS** | 9.8 | -13.9 dBFS |
| Kodik 720p | **-24.6 LUFS** | 13.5 | -11.1 dBFS |
| YouTube | **-20.9 LUFS** | — | -0.1 dBFS |
| **Разброс** | **19.0 дБ** | | |

19 дБ — это шёпот против крика. Ползунок в игре один, а источники разные:
на Rutube не слышно, на Kodik соседи стучат.

**Решение.** Нормализация к -16 LUFS (интернет-стандарт):
1. один замер ffmpeg `ebur128` + `astats` (3 секунды);
2. кэш на 6 часов рядом с ссылкой;
3. усиление уходит в браузер как `GainNode` — **без перекодирования
   и без CPU на лету** (важно при 8 ГБ ОЗУ и запущенной GTA 5).

**Результат:** разброс 19.0 → **11.0 дБ (сужение 42%)**.

Почему не ровно -16 у всех: у Rutube пик -13.9, поднимать можно только
на 12.9 дБ. Дальше — клиппинг. Честно тише, чем с искажениями.

**Найденный по пути баг.** Тихий звук с высоким пиком (YouTube: -20.9 LUFS
при пике -0.1) получал усиление **-0.9 дБ** — то есть становился ЕЩЁ ТИШЕ
и уходил от цели дальше. Причина: «запас до пика» = -1 - (-0.1) = -0.9,
и это отрицательное число подставлялось как предел. Правило: если поднимать
некуда — **не трогать**, а не опускать.

**Урок.** «Нормализация» — не «поднять всё до цели». Это «привести к цели
настолько, насколько позволяет пик, и не испортить».

## ERR-081 — Kodik «Видео не воспроизводится»: levelLoadError

**Дата:** 23.11.2026
**Жалоба заказчика:** та же ссылка, озвучка СВ-Дубль — у него `levelLoadError`,
у меня видео играет. Скриншот в `uploads/image-8.png`.

### Что оказалось

Ссылка живая: срок в адресе `2026112411` (в моём тесте был `2026112404`),
то есть **свежее моей**. Дело не в протухании.

Причина — **обрыв соединения без ответа**. Три сценария, все воспроизведены:

| Сценарий | Было | hljs.js видел |
|---|---|---|
| Зеркало p12/p13/p14 не ответило | `RuntimeError` из `_probe_playlist` → сокет закрыт | `levelLoadError` |
| CDN отдал 404 | то же | `levelLoadError` |
| В URL не-ASCII (кириллица) | `UnicodeEncodeError` → сокет закрыт | `levelLoadError` |

`_serve_hls` не ловил исключения, и `BaseHTTPRequestHandler` рвал связь
молча. Снаружи это выглядит как «поток не воспроизводится», хотя 720p жив.

### Исправлено

1. **`_serve_hls` ловит любое исключение** и отдаёт настоящий `502` с
   причиной в теле (`#EXT-X-KODIK-ERROR:...`). hls.js теперь видит сетевую
   ошибку уровня, пробует другое качество и пишет деталь в журнал.

2. **Проверка зеркал перед сборкой master** (`_probe_alive_qualities`):
   три запроса параллельно, 6 с на все. Мёртвые качества не попадают в
   master — hls.js не может выбрать неработающее зеркало.
   Если проверка не удалась целиком (нет сети) — отдаём всё как есть:
   пустой master хуже мёртвого зеркала.

3. Проверка на 8 ГБ: замер параллельный, резолв замедляется на 0.4 с.

### Урок

«Обрыв» и «502» для hls.js — разные вещи. Обрыв он видит как сетевую
ошибку без причины и не может переключиться. Явный код + тело позволяют
ему выбрать другое зеркало, а разработчику — увидеть причину в журнале.

## ERR-083 — Мастер ссылался мимо моста: видео молча не играло

**Дата:** 24.11.2026
**Где:** `web/server.py`, `_stream()`

**Симптом.** Плеер открывается, ошибок нет, в журнале ни строки — и чёрный
экран. Воспроизводилось не на всякой машине: локально поток играл.

**Разбор.** `/stream/<sid>` собирал master-плейлист с **прямыми адресами
источника** и оставлял комментарий «ссылки в master абсолютные — мост
перепишет их сам». Переписывать было некому: мастер уходит браузеру как
есть. Мост работает только для ссылок, которые уже обёрнуты в
`/hls?url=…`.

**Почему не ловилось.** Локальная проверка шла с той же машины, где домены
источника доступны напрямую, а файлы склейки лежат на диске. В игре CEF
чужой домен открыть не может, `file://` — тем более.

**Решение.** `_stream` оборачивает каждое качество и аудиодорожку в
`proxify()` до сборки мастера. Два теста: ссылки в мастере обязаны
начинаться с `/hls?url=`.

**Урок.** Комментарий «это сделает кто-то другой» — не выполненная работа.
Если в комментарии написано, что ссылки будут переписаны, нужно найти
строку, где это происходит. Её не было.

## ERR-084 — Склейка YouTube: качество указывало не на склейку

**Дата:** 24.11.2026
**Где:** `sources/youtube.py`, `_via_mux()`

**Симптом.** Для видео без HLS-аудио запускался ffmpeg, сегменты писались
на диск — а в плеере видео шло без звука. То есть аварийный путь не решал
проблему, ради которой существовал.

**Разбор.** Метод возвращал `Quality` с адресом **исходного** плейлиста
источника, а не склеенного. Дальше плеер шёл по исходному адресу, ffmpeg
отрабатывал впустую.

**Почему не ловилось.** Тест проверял заголовок «(склейка)» и что качество
одно. Адрес, то есть единственное, что важно, не проверялся.

**Решение.** Возвращается `mux.local_playlist_path(muxed)`, плюс
`wait_ready()` — ждём первый сегмент, иначе плеер покажет ошибку раньше,
чем появится картинка. Тест проверяет сквозное воспроизведение в Chromium:
декодированные байты видео и звука.

**Урок.** Тест, который смотрит на название, а не на адрес, проверяет
название. Проверять надо то, что реально влияет на работу.
