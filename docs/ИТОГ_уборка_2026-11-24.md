## 1. Утечки памяти — нашлись, и не там, где искали

Первым делом я снял замер: `tools/bench_memory.py --quick` дал 45,9 МБ
пика и +0,1 МБ на десять сессий. По этому замеру выходило «утечек нет».

Вывод был неверным. Насторожило другое: **после закрытия сессий память не
возвращалась** — 45,9 МБ и оставались. Значит память держится не ссылками
запроса, а чем-то живущим в процессе. Дальше — четыре неограниченных
словаря:

| Что | Почему росло | Стало |
|---|---|---|
| `SessionStore` | TTL 6 часов, предела по числу нет | 64, вытеснение по давности |
| `cvh.CACHE` | плейлисты по 615 КБ, без предела | 8 |
| `cvh.SIZES` | размеры кадра, без предела | 256 |
| `yummy._cache/_titles/_players`, `kodik_embed._cache` | обычные `dict`, растут с каждой страницей | `TTLCache(32, 600 с)` |

Корень один и он не очевидный: **TTL проверялся только при чтении
ключа**. К ключу, к которому не вернулись, никто не читает — запись не
удаляется никогда. Срок жизни без предела числа не чистит ничего.

Замерено на 25 000 сессий: **+10,6 МБ до правки, +0,0 МБ после**, в
хранилище 64 записи. Пять тысяч плейлистов: 8 в кеше, 256 размеров, RSS
39,9 МБ.

Вместо четырёх самодельных копий — один `core/cache.py`: `TTLCache`
(предел + TTL), `SizeCache` (предел), `file_key` (ключ файла по id из
адреса, а не по подписи, которая меняется каждые минуты). Заодно
`SessionStore.delete` и `drop` делали одно и то же — оставлен `drop`.

17 тестов в `tests/v2/test_bounded_caches.py` проверяют предел, вытеснение
самого давнего, TTL и — отдельно — что боевые кэши ограничены. Это важнее
отчёта: замер забывается, тест нет.

**Скорость.** Утечки и скорость — это одна задача: без предела словарь
растёт, и поиск в нём замедляется. Пределы заодно вернули скорость:
`cvh.SIZES` из ограниченного словаря отвечает за один шаг, а проба
размера — это GET на 256 КБ, который повторно не делается.

Сохранено: токен и helper для git (вне репозитория), `videos/registry.json`
(под версией — в нём примеры для проверки, а не мусор), вся документация,
