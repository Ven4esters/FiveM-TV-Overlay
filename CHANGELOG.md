# 2.2.5: POST /new не работал, README врал про HTTP API — 26.11.2026

Проверял не глазами, а живыми запросами к запущенному серверу. Нашлось два
дефекта, которые не видел ни один тест, потому что сам пульт ходит в обход
сломанных мест.

## 1. `POST /new` отвечал 404

README обещает: `POST /new?url=<ссылка>` создаёт сессию. В
`_route_post` этого пути **не было вовсе** — работал только GET, потому что
пульт ходит GET-ом (`ui/api.py`). Любой внешний клиент — скрипт, другой
пульт, интеграция — по документации получал «нет маршрута /new».

```
было:  curl -X POST /new?url=...  →  {"error": "нет маршрута /new"}
стало: curl -X POST /new?url=...  →  {"ok": false, "reason": "Rutube: ..."}
```

Второй ответ — правильный: сервер разбирает ссылку и объясняет, почему
источник не отдал видео. GET-путь сохранён: им пользуется пульт.

## 2. README обещал `/commands`, а сервер отвечает на `/cmd`

Расходились **7 маршрутов из 23**:

- обещан несуществующий `/commands/<sid>` вместо `/cmd/<sid>`;
- не описаны вовсе: `trans`, `episode`, `history/forget`, `close`, `trace`,
  `report`, `hls`, `stream`, `subs`, `loudness`, `static`, `index.html`;
- у `trans` и `episode` параметр назван `id`/`n`, а в коде он `index`.

Проверено каждое утверждение запросом к живому серверу, а не чтением кода.

## 3. Чтобы это не повторилось — проверка, а не надежда

`tools/check_api_docs.py` извлекает маршруты из `server.py` и из обеих
таблиц README и сравнивает множества. Запускается в CI (`readme-checks.yml`,
задание `consistency`) и локально тестом `test_225_*`.

Проверка не декоративная: на подложенной ошибке `/cmd` → `/commands` она
краснеет с точным текстом «обещан маршрут /commands, которого нет в коде».
Сам скрипт зависит только от стандартной библиотеки — не требует установки.

## 4. Что сознательно не менял

`POST /close/<sid>` для несуществующей сессии отвечает `ok: true`. Это
идемпотентность, а не ошибка: повторное закрытие не должно падать. Отмечено
здесь, чтобы не выглядело недосмотром.

## 5. Итог

```

ruff format / ruff check / mypy — чисто
маршруты в README и коде совпадают: 23
```

# 2.2.4: гейты CI, которые пропускали падения, и README без заметок — 26.11.2026

Три правила этого раунда: CI должен ловить, README — говорить с пользователем,
релиз не делаем.

## 1. Гейт, который пропускал падение

Шаг «Тесты с покрытием» стоял с `continue-on-error: true`, а вердикт выносил
следующий шаг — поиском строки `N failed` в журнале. Проверено на подставных
журналах, что такой гейт пропускает:

| Что произошло | Вид в журнале | Старый гейт |
|---|---|---|
| Покрытие ниже порога | `FAIL Required test coverage of 68.0% not reached` | пропускал |
| Модуль не собрался | `ERROR tests/...` | пропускал, если был хоть один `passed` |
| Pytest не запустился | пустой файл | пропускал |
| Модуль не импортируется | `ERROR collecting tests/...` | пропускал (слово `error` в нижнем регистре) |

Причина в устройстве: в строке о покрытии нет слова «failed», а слово
«ERROR» в выводе pytest написано заглавными. Гейт смотрел на текст, а не на
код возврата. Теперь `continue-on-error` убран, работает `set -o pipefail`,
и значение имеет код возврата pytest. Шаг-обманка удалён.

`test_224_*` держит это: читает workflow как YAML и проверяет, что у шага
тестов нет `continue-on-error` и есть `pipefail`. Именно YAML, а не текст —
первая версия теста спотыкалась о слово `continue-on-error` в собственном
пояснении к коду.

## 2. Ещё три гейта, которые ничего не проверяли

- **Порог покрытия.** Шаг печатал `fail_under` из `pyproject.toml` — константу
  из конфига. Зелёным он был всегда, при любом покрытии. Теперь берёт
  `line-rate` из `coverage.xml` и падает, если факт ниже порога.
- **SCA (уязвимости зависимостей).** Стояло `|| echo "::warning::..."` —
  шаг зелёный при любом результате. Вдобавок проверялся `requirements.txt`
  (три строки без версий), а не то, что реально ставится. Теперь блокирует и
  сканирует установленное окружение.
- **Регресс на живых источниках.** Код 5 («ничего не выбрано») считался
  нормой, поэтому маркер `network` мог исчезнуть вместе с тестами, и задание
  осталось бы зелёным, ничего не проверяя. Теперь это ошибка.

## 3. Windows-сборка пересобирается при правках кода

`paths` следил за одним файлом (`core/ffmpeg_bin.py`). Правка любого другого
модуля не запускала сборку, и «ffmpeg внутри .exe» мог сломаться молча.
Теперь триггер — весь `src/**`, `pyproject.toml` и `tvhost.spec`.

## 4. README: только то, что нужно пользователю

Из README убрано то, что было запиской разработчику:

- два блока `<!-- TODO(exe) -->` и `<!-- TODO(virustotal) -->` с порядком
  действий «собрать, вставить, заполнить» и пустой таблицей `TODO` — читатель
  видел недоделанный продукт;
- «см. чек-лист в `docs/images/README.md`» — внутренний файл процесса;
- «последний прогон зелёный» — утверждение, которое стареет само по себе;
- из подписи внизу убрано «поддерживается только v2.1; код v1 остался тегом» —
  это история разработки, а не свойство продукта.

Исправлено то, что врало: бейдж версии и подпись показывали **2.1.0** при
коде 2.2.3 (три релиза подряд), число тестов — **493** при фактических 634.

Осталось то, что нужно читателю: как проверить свой файл (`Get-FileHash`,
`certutil`, `sha256sum`), что делать при срабатывании антивируса, требования,
быстрый старт, сборка, использование, HTTP API, ограничения, FAQ.

## 5. Проверки README в CI

Новое задание `consistency` в `readme-checks.yml` — машинные проверки вместо
надежды на внимательность:

- версия в бейдже и подписи совпадает с `__version__` в коде;
- в README нет `TODO`, `FIXME` и «заполним после»;
- каждый якорь оглавления ведёт на существующий заголовок;
- `<details>` закрыты, алерты на месте.

Каждая проверка прогнана на заведомо плохом файле: битый якорь ловится,
`TODO` ловится, расхождение версии ловится.

## 6. Что вскрыл честный гейт в первый же прогон

Как только шаг тестов перестал глотать код возврата, CI покраснел — и не
зря. Два настоящих дефекта, которые до этого жили спокойно:

**Процесс pytest падал с SIGSEGV (код 139), хотя все тесты проходили.**
В конце вывода стояло `QObject: shared QObject was deleted directly. The
program is malformed and may crash`. Причина: тесты создают `Panel()` и не
уничтожают его — объект остаётся жив до выхода из интерпретатора и удаляется

`tests/conftest.py` закрывает и удаляет виджеты сразу после каждого теста.
Проверено: три UI-модуля и полный набор возвращают 0.

**`pyyaml` не был объявлен в зависимостях.** Тест проверки гейтов читает
workflow как YAML; у разработчика PyYAML стоял, в CI — нет. Добавлен в
dev-зависимости; сам тест без него пропускается с понятной причиной.

# 2.2.3: почему не находился ffmpeg, и почему в исходниках он «был» — 26.11.2026

Вопрос: «Почему он не находит ffmpeg, если он устанавливается в зависимости
и должен идти в компилируемый .exe?» Разбор по шагам, потому что причина
оказалась не в зависимостях, а в сборке.

## 1. Зависимость была. Сборка её теряла

`imageio-ffmpeg>=0.4.9` стоит в `pyproject.toml`, `requirements.txt` и
`requirements-v2.txt`, `build.bat` его ставит (`import PySide6, yt_dlp,
imageio_ffmpeg` проходит). То есть **пакет** в сборке был.

Бинарник — нет. `imageio-ffmpeg` держит ffmpeg файлом внутри себя
(`imageio_ffmpeg/binaries/ffmpeg-win-x86_64-v9.0.2.exe`) и находит его через
`importlib.resources.files("imageio_ffmpeg.binaries")`, то есть ему нужна
**настоящая папка с файлом**. В `--onefile` всё распаковывается во временную
папку, и файл должен быть среди данных сборки. В `tvhost.spec` было
`binaries=[]`, а `imageio_ffmpeg` — только в `hiddenimports`; `hiddenimports`
включает в сборку **модули**, но не файлы-данные.

Почему ошибка не всплывала раньше: на Linux PyInstaller-хук подхватывал
бинарник сам, и проверка «ffmpeg нашёлся» проходила. На Windows тот же хук
файл не забирал — и в .exe ffmpeg отсутствовал. Отсюда «в исходниках
работает, в .exe — нет».

Проверено на деле: тестовая сборка `--onefile` на Linux отдавала
`/tmp/_MEI…/imageio_ffmpeg/binaries/ffmpeg-linux-x86_64-v9.0.2`,
`EXISTS: True` — то есть подхват есть, но он зависит от платформы, и на него
нельзя рассчитывать.

## 2. Что исправлено

- `tvhost.spec`: ffmpeg кладётся в сборку **явно** —
  `binaries=_ffmpeg_binaries()`, из `imageio_ffmpeg.get_ffmpeg_exe()` (а если
  пакет есть, а файла нет — поиском по его папке `binaries`). Нет пакета —
  сборка идёт без ffmpeg, а не падает.
- `core/ffmpeg_bin.py`: добавлен шаг поиска по распакованной сборке
  (`sys._MEIPASS/imageio_ffmpeg/binaries/ffmpeg*.exe`, затем `bin/` и папка
  рядом с программой). Причина: `get_ffmpeg_exe()` сверяет файл с **жёстко
  заданным именем** для платформы (`ffmpeg-win-x86_64-v9.0.2.exe`). Попала в
  сборку другая версия — он честно отвечает «нет», хотя ffmpeg лежит рядом.
  Теперь имя значения не имеет.
- Новый маршрут **`/diag/ffmpeg`**: отвечает, что видит **сама собранная
  программа** — путь, `exists`, `runs`, первые байты баннера, `frozen`.
  Раньше «не находит» приходилось угадывать издалека.

## 3. Проверка на настоящей Windows

Добавлен `.github/workflows/windows-build.yml` (`runs-on: windows-latest`):
ставит зависимости, печатает, что скачал `imageio-ffmpeg`, собирает по
`tvhost.spec`, запускает .exe и **спрашивает у него** `/diag/ffmpeg`. Ответ
попадает в журнал прогона, .exe — в артефакты. Это защита от повторения:
раньше Windows-сборки в CI не было вообще, поэтому «в .exe нет ffmpeg»
могло жить сколько угодно.

## 5. Почему CI был красным (и это не связано с ffmpeg)

Пока проверялся Windows-прогон, выяснилось, что `ci.yml` падал **и до**
правок этого раунда. Две причины, обе не в коде приложения:

- **`ruff format --check` не проходил** на 7 файлах. Локально запускались
  только `ruff check` и `mypy`, поэтому расхождение копилось незаметно.
  Теперь проверяются все три, и все три чисты.
- **`ImportError: libEGL.so.1`** — 26 тестов интерфейса падали на
  `ubuntu-latest`, потому что там нет библиотек Qt, а тесты создают
  `QApplication`. Локально они проходили именно потому, что библиотеки были.
  В CI добавлены `libegl1`, `libgl1`, `libxkbcommon*`, `libxcb-*` и
  `QT_QPA_PLATFORM=offscreen`. Это дефект окружения, а не кода: чинить его
  в приложении было бы неправильно.

Ещё: `git add -A` затянул в коммит папку `.tmp/` с пробами PyInstaller
(сгенерированные `.spec`, junit-отчёт, симлинки на системные библиотеки), и
`ruff check .` в CI честно ругался на них как на исходники. `.tmp/` и
`build-venv/` теперь в `.gitignore`, а из репозитория удалены.

## 6. Подтверждено на настоящей Windows

Не на глаз и не «должно работать»: файл собран на `windows-latest` и запущен.

```
exe: dist\FiveM-Video-Overlay.exe bytes=87881261
entries in bundle: 254
ffmpeg entries in bundle: ['imageio_ffmpeg\\binaries\\README.md',
                           'imageio_ffmpeg\\binaries\\ffmpeg-win-x86_64-v9.0.2.exe']
OK: ffmpeg binary is inside the exe

SELFTEST ffmpeg=C:\Users\RUNNER~1\AppData\Local\Temp\_MEI0000270c2\imageio_ffmpeg\binaries\ffmpeg-win-x86_64-v9.0.2.exe
SELFTEST version=9.0.2-essentials_build-www.gyan.dev
SELFTEST frozen=True
OK: ffmpeg is inside the build and resolved
```

То есть ffmpeg не просто лежит внутри, а **находится и запускается** самим
кодом программы в распакованной папке `_MEI…` — ровно там, где раньше
поиск молча возвращал «нет».

Что ещё попутно вскрылось при этих прогонах:

- `timeout /t` в cmd падает с «Input redirection is not supported» — поэтому
  проверка идёт через `--selftest`, без ожиданий и без HTTP;
- приложение в CI не поднимается вовсе (нет рабочего стола, неполные
  Qt-плагины), так что проверка через `/diag/ffmpeg` мерила бы наличие Qt.
  Маршрут оставлен для людей: на машине с экраном он отвечает сразу.

## 7. Как проверить у себя

Запустить и открыть в браузере `http://127.0.0.1:9001/diag/ffmpeg`:

```json
{"found": true, "frozen": true, "exists": true, "runs": true,
 "path": "C:\\...\\_MEI...\\imageio_ffmpeg\\binaries\\ffmpeg-win-x86_64-v9.0.2.exe"}
```

`found: false` — ffmpeg действительно нет в сборке (тогда смело присылайте
тот же ответ). `found: true, runs: false` — файл есть, но не запускается:
обычно антивирус или битая загрузка.

# 2.2.2: anidub.com открывал первую серию, 502 на сегментах, замер и уведомления — 26.11.2026

Отчёт на 2.2.1. Два пункта из пяти оказались не тем, чем выглядели, и один
закрыт полностью.

## 1. anidub.com: «разные серии приводят к одной» — корень найден

Доказано побайтово: серии 1, 3, 4 и 18 отдавали **один и тот же сегмент**
(md5 `399a97e419fb`, 3 332 304 байта). Не кэш и не наш код нумерации.

Дело в устройстве плеера `ladonyvesna`. У каждой серии свой путь:

```
1 серия  → /s2/88641d95dee4f2e746bc134e6207f5fa
3 серия  → /s2/90ccd33faacbca76d39e6cf80d5c9e1b
4 серия  → /s2/8ee77efff9f36ff502ee1651f3b64897
```

а мы подставляли номер параметром `?episode=N`, который плеер **молча
игнорирует** (в его конфигурации `"hasSeries":false` и жёстко заданный
`currentEpisodeKey`). Плюс список серий запрашивался **без `&playlist`** — с
ним плеер отдаёт все 157 записей с их `link` и `key`, без него `"episodes":[]`.

Теперь берём `link` нужной серии и подставляем его в путь плеера. Проверено:
у серий 1, 3, 4 — три разных пути, и открывается именно запрошенная серия.

Заодно объяснилась «дыра» в нумерации: в описании самого сайта написано
«Первая серия совмещена, и включает в себя 1 и 2 серии».

## 2. Kodik: 502 и «серия не запускается» — это были сегменты

Замер: сегмент anidub.com (3 МБ) приходил **22 секунды**. Мы копили его в
память целиком и только потом отдавали — hls.js сдавался, повторял запрос,
повтор лез в тот же медленный канал, и в журнале появлялся
`fragLoadError HTTP 502`.

Теперь сегменты отдаются **потоком**, по мере скачивания:

```
было:  первый байт 22.45 с, целиком 22.45 с
стало: первый байт 1.10 с,  целиком 1.99 с
```

Плейлисты по-прежнему идут через `fetch` — их надо переписывать. Тип
определяется по адресу, без скачивания.

## 3. Пропадающее уведомление про субтитры

Опрос идёт каждые 800 мс и тут же ставил обратно «играет 0:00 / 0:00».
Теперь ответы на действия «прилипают»: сообщение держится 4–7 секунд и
переживает опрос (проверено — четыре опроса подряд).

## 4. «Замер не удался» — причина названа

Две разные беды сливались в одно сообщение. Теперь:

* нет ffmpeg → «нужен ffmpeg» + «Положите ffmpeg.exe рядом с программой
  (в папку bin) или установите: winget install ffmpeg»;
* поток не читается → «замер не удался» + «нормализация необязательна —
  звук играет и без неё».

остальные. Покрыто тестами на 8 типов значения, включая `bool`, `str`,

# 2.1.4: OK.ru отдавал 400 без User-Agent — 25.11.2026

При повторной проверке живых ссылок OK.ru снова не заиграл, хотя сессия
создавалась и качества находились. Отказ был на первом сегменте: `HTTP 400`
с телом `10`.

## Причина

Подпись okcdn (`sig=` в `manifest_url`) привязана к отпечатку клиента.
Проверено перебором заголовков на одном и том же адресе:

| Заголовки | Ответ |
|---|---|
| никаких | `400`, тело `10` |
| только `Accept` | `400`, тело `10` |
| только `User-Agent` | **`200`, плейлист** |
| полный набор браузера | `200`, плейлист |
| `User-Agent` + `Referer` | `200`, плейлист |

То есть достаточно любого `User-Agent` — а `Stream` для OK.ru уходил
**вовсе без заголовков**. Механизм передачи у сервера уже был
(`Stream.headers` → `_stream_headers()` → `fetch()`), им пользуется
anidub.org; OK.ru его просто не заполнял.

Почему не поймали раньше: тесты на заглушках проверяли разбор ссылки и
отбор качеств, а не живой CDN. Симптом («сессия есть, видео чёрное»)
выглядел как проблема плеера.

## Что исправлено

`OkRuSource.resolve()` заполняет `Stream.headers`:

```python
headers={"User-Agent": USER_AGENT, "Referer": "https://ok.ru/"}
```

`USER_AGENT` — Chrome 140 на Windows. Значение не случайное: подпись
привязана к `srcAg=CHROME`, и UA обязан соответствовать.

Тест `test_stream_carries_user_agent` в `tests/v2/test_okru.py` падает,
если заголовки снова пропадут.

# 2.1.3: .exe слушал порт, но не отвечал ни на один запрос — 25.11.2026

Отчёт с собранной 2.1.2 показал точную картину:

```
порт: 127.0.0.1:9001 — слушает
проверка: не отвечает: Remote end closed connection without response
```

Порт слушает, сервер жив, но каждый запрос обрывается без ответа. Из-за
этого пульт писал «прокси: выключен», источники молчали, журнал сервера
был недоступен.

## Причина

```
send_response() → log_request() → log_message() → sys.stderr.write(...)
```

В сборке PyInstaller с `console=False` у процесса нет консоли, и
`sys.stderr` там равен **None**. `sys.stderr.write` — это
`AttributeError: 'NoneType' object has no attribute 'write'`, причём
возникает он ВНУТРИ `send_response`, то есть **до отправки заголовков**.
Клиент видит оборванное соединение.

Вторая беда: `socketserver` печатает трейсбеки в тот же отсутствующий
stderr, поэтому сбой был полностью невидим — ни в окне, ни в файле.

Совпадение симптомов с прошлым багом («прокси: выключен») было полным, но
причина другая: там запрос уходил на чужой прокси, здесь — запрос доходил,
а ответ падал. Отчёт 2.1.2 и позволил их различить: `порт — слушает` против
`порт — никто не слушает`.

## Что исправлено

**1. `OverlayHandler.log_message` больше не пишет в stderr.** Один метод —
и причина исчезла целиком: `send_response` больше не падает. Запросы
пишутся в собственный журнал (`diagnostics`), подробный лог каждого
запроса там и не нужен.

**2. `handle_one_request` перехватывает сбои разбора запроса** и пишет их в
журнал. Раньше трейсбек уходил в `socketserver` → stderr → никуда.

**3. `core/startup.py` — подготовка процесса без Qt:**
   * `ensure_streams()` подставляет заглушки вместо `None` в
     `sys.stdout`/`sys.stderr` — на случай чужого кода, который пишет туда
     напрямую;
   * `install_crash_log()` — необработанные исключения в журнал;
   * `mark_startup()` — отметка запуска до создания окна.

   Модуль намеренно без PySide6: он обязан работать, даже если Qt не
   загрузился, — иначе диагностика исчезает ровно тогда, когда нужна.

**4. `ui/theme.py`** тоже проверяет поток перед записью.

## Тесты

`tests/v2/test_no_stderr_frozen.py` (8 тестов). Ключевой урок: **первая
версия теста была бесполезной**. Он подменял `sys.stderr` через
`monkeypatch`, но pytest перехватывает стандартные потоки и восстанавливает
их, поэтому подмена до сервера не доходила — тест проходил на сломанном
коде. Теперь ломается то, что читает поток: `log_message` базового класса
из stdlib. Проверено откатом: без фикса падают 4 теста, с фиксом проходят
все 8.

# 2.1.2: диагностика, которая работает при мёртвом сервере — 25.11.2026

Жалоба: «прокси не работает, источники молчат, **журнал пуст**». Третий
пункт — самый важный: он означал, что зацепок нет вообще.

## Почему журнал был пуст

Пульт журнал только **читал** (через `/diag` у сервера), а писал в него
только сервер. Если сервер не поднялся — читать нечего. Плюс сам файл
журнала лежал по относительному пути `videos/cache/overlay.log`, то есть
считался от текущего каталога процесса: при запуске из ярлыка или из другой
папки он оказывался не там, где его искали. В довершение `_append_file`
глушил `OSError` — если писать не удавалось, об этом никто не узнавал.

## Что сделано

**1. Пульт пишет в журнал сам.** Новый `Panel._local()` кладёт строку и в
окно, и в файл, не спрашивая сервер. Каждая неудача оставляет след:

* `проверка прокси на порту N`;
* `прокси не отвечает на порту N: <никто не слушает | не отвечает | слушает>`;
* `источники не загрузились: <причина>`;
* `журнал сервера недоступен: <причина>`.

**2. Журнал рядом с приложением.** `LOG_PATH` теперь считается через
`resources.app_dir()`: в сборке это папка `.exe`, в исходниках — корень
проекта. Один и тот же путь в отчёте и в подсказке.

**3. Запись с самой первой секунды.** `ui/__main__.py` ставит `mark_start()`
и пишет строку о запуске **до** создания `QApplication` — если падение
случится на старте, след останется. Необработанные исключения перехватывает
`sys.excepthook` в `tvhost2_entry.py` и тоже пишет их в журнал: в сборке
`console=False` трейсбек иначе увидеть негде.

**4. Кнопка «Отчёт».** Новый модуль `core/diag_report.py` собирает снимок:
версия, пути, `frozen`, Python, yt-dlp, ffmpeg, **состояние порта**,
**реальный запрос к серверу**, **системный прокси** и хвост журнала.
Копируется в буфер одной кнопкой на вкладке «Журнал». Собирается даже когда
сервера нет — именно для этого случая и сделан.

Пароли прокси в отчёт **не попадают**: `http://user:pass@host` печатается
как `http://***@host`.

**5. Иконка в шапке.** Там рисовалась схематичная киноплёнка (`film.svg`),
хотя у `.exe` и панели задач была своя иконка. Теперь в шапке `logo.svg` —
тот же телевизор с кнопкой Play и теми же цветами, но без тёмной плашки:
на тёмном фоне окна плашка сливалась.

## Тесты

`tests/v2/test_diag_report.py` (18 тестов): путь журнала привязан к
приложению, запись доходит до диска, незаписываемый путь не роняет
программу, `port_state` различает «слушает» и «никто не слушает», `probe`
опознаёт свой сервер и не путает его с чужим, пароль прокси маскируется,
отчёт собирается без сервера.

# .exe падал на относительном импорте — 25.11.2026

Заказчик собрал .exe и получил при запуске:

```
Unhandled exception in script
Failed to execute script '__main__' due to unhandled exception:
attempted relative import with no known parent package
File "__main__.py", line 26, in <module>
ImportError: attempted relative import with no known parent package
```

## Причина

`tvhost.spec` указывал точкой входа файл `src/tvhost2/ui/__main__.py`. PyInstaller
исполняет указанный скрипт как **модуль верхнего уровня, вне пакета**. А внутри
этого файла стоят относительные импорты:

```python
from ..core import resources   # строка 26 — та самая
from . import theme
from .api import Api
from .panel import Panel
```

Относительному импорту нужен известный родительский пакет (`tvhost2.ui`), а при
запуске «как скрипт» его нет. В исходниках ошибки не видно, потому что там файл
запускают как `python -m tvhost2.ui` — тогда пакет известен.

Ошибка воспроизведена в изоляции: та же структура пакета, тот же запуск «как
скрипт» — тот же `ImportError` на первой же относительной строке.

## Решение

Создан `src/tvhost2_entry.py` — тонкая обёртка с **абсолютным** импортом:

```python
from tvhost2.ui.__main__ import main as panel_main
```

Пакет при этом загружается целиком, и все относительные импорты внутри него
работают как обычно. `tvhost.spec` переведён на эту обёртку.

Поведение .exe не изменилось: запускается тот же `main()`, что и у
`python -m tvhost2.ui`, то есть `--serve` по умолчанию включён (в сборке
`resources.FROZEN` истинно).

## Тест

`test_entry_point_uses_absolute_import` проверяет три вещи: в spec указана
обёртка, прямой `ui/__main__.py` не указан, и в самой обёртке нет ни одного
относительного импорта. Без него эта ошибка вернулась бы при первой же правке
spec.

## Отчёт для README

`build.bat` теперь пишет рядом с .exe файл **`FiveM-Video-Overlay.exe.txt`**:
версия (из `pyproject.toml`, а не вписанная руками), размер в байтах и МБ, дата
сборки, MD5, SHA-256, готовые команды проверки для PowerShell / cmd / Linux и
список файлов на выходе. Данные копируются в README, раздел «Проверка файла»,
как есть — вручную ничего сверять не нужно.

Скрипт заодно приведён к виду образца заказчика: короткие шаги `[1/7]`,
`goto :venv_ready`, метки `:built`-стиля (`:failed`), `pause` на обоих путях.

# build.bat не запускался — 25.11.2026

Заказчик прислал скриншот: PowerShell пишет «Имя build.bat не распознано как
имя командлета», а при двойном клике окно схлопывается без сообщений.

## Почему не запускалось

**1. PowerShell не ищет программы в текущей папке.** Это его защита от
подмены команд: `build.bat` без ` .\` он не запустит никогда. Правильно:
` .\build.bat` или просто двойной клик по файлу.

**2. Скрипт был в UTF-8 с `chcp 65001`.** Вот это и есть «схлапывается»:
`cmd.exe` с UTF-8 в batch-файле работает нестабильно — сам Microsoft в блоге
«The Old New Thing» пишет, что обработка batch становится unstable. На русской
Windows консоль по умолчанию в CP866, и первая же строка с кириллицей может
уронить разбор. Чинится не флагами, а кодировкой файла.

## Что сделано

- **`build.bat` переписан в CP866** — родная кодовая страница консоли русской
  Windows. `chcp` убран совсем: он больше не нужен, а именно он ломал разбор.
  В шапке файла написано, что пересохранять в UTF-8 нельзя.
- **То же для `start.bat` и `check_link.bat`** — в них была та же мина. Оба
  тоже переведены в CP866 и лишились `chcp 65001`.
- **Журнал `build-log.txt`.** Каждая строка, которую печатает скрипт,
  дублируется в файл. Теперь «схлопнулось и ничего не произошло» разбирается:
  если журнала нет вообще — дело в самом .bat; если есть и обрывается —
  видно, на каком шаге.
- **`pause` на обоих путях** (успех и провал): окно не закроется, пока не
  нажмут клавишу.

- Все три `.bat`: CP866, без BOM, ровно CRLF (смешанные переводы строк — одна

- Подпрограммы стоят после `exit /b 0`: поток выполнения в них не провалится.

## 1. `build-venv/` — сборка больше не зависит от `start.bat`

Раньше `build.bat` искал `.venv\Scripts\python.exe`, созданный `start.bat`,

  venv, и раньше это выглядело как «сборка упала без причины».

# Сборка .exe — 24.11.2026

## build.bat — автономный .exe и контрольные суммы

Заказчик: «создай build.bat, который собирает .exe; компилировать сам не надо,
сделаю локально. Он же должен создавать .exe.md5 и .exe.sha256».

- `build.bat` — шесть шагов с проверками на каждом: Python (и разрядность:
  32-битный соберёт .exe, который не запустится), зависимости, чистка,
  сборка, контрольные суммы, итог. Любой сбой останавливает сборку с
  понятным текстом, а не оставляет половину файлов.
- `tvhost.spec` — конфигурация PyInstaller отдельно от командной строки:
  файлов данных три (страница плеера с `hls.min.js`, `style.qss`, иконки), в
  флагах их легко потерять. Исключены Qt WebEngine/Multimedia/Quick, UPX
  отключён.

## Что пришлось починить, чтобы .exe вообще заработал

Это не «сборка ради сборки»: три вещи в коде были написаны так, что из
исходников работают, а в собранном файле — нет.

1. **`Path(__file__).parent` в onefile ведёт в распаковку.** Создан
   `core/resources.py` с двумя разными понятиями: `resource()` — файлы
   внутри приложения (только чтение), `app_dir()` — папка, где можно писать
   и где лежит `.exe`. На него переведены `server.py`, `ui/theme.py` и
   `core/ffmpeg_bin.py`.
2. **Ошибка в первой версии `resource()`**, которую поймал тест до сборки:
   путь принимался как `"..", "web", "static"` и в сборке давал
   `<распаковка>/tvhost2/../web/static` — папку на уровень выше пакета, то
   есть пустую. Теперь путь считается от корня пакета и `..` не нужен.
3. **Двойной клик по .exe не передаёт аргументов**, а `--serve` был выключен
   по умолчанию: пульт открылся бы без сервера и не работал. Теперь в
   сборке `--serve` включён по умолчанию (`resources.FROZEN`), из исходников
   поведение прежнее, `--no-serve` отключает.

Плюс дефект в самом `build.bat`, найденный проверкой на симуляции вывода
`certutil`: он печатает хеш ЗАГЛАВНЫМИ, а `findstr` искал строчные — MD5
остался бы пустым, и сборка падала бы **всегда**, на ровном месте, уже
после успешной компиляции. Исправлено (`findstr /i` плюс приведение к
нижнему регистру для читаемости).

  гасить 310 замечаний архива списком исключений — не то же самое, что
  содержать код в порядке. Проверено установкой в чистое окружение: страница 200,
  `hls.min.js` 200 (413 КБ).

- **Alloha удалена (26.11.2026).** Плеер разобран до конца — вплоть до
  подписанного пропуска в `Borth` из меты страницы, — но сервер не отдал
  адреса ни на одной из десяти проверок, в том числе с точным повтором
  запроса браузера, настоящим отпечатком и свежим пропуском. Заказчик
  отказался от плеера. Удалены: источник, диагностика (`alloha_check`,
  `replay_alloha`), тесты и разборы в `docs/`. Сайты zlord.org,
  lordserialc.run и mltclb2.icu больше не поддерживаются.

- **История просмотров** — недавние в пульте, до пяти, в памяти на одну
  сессию. Клик по записи открывает видео заново. Дедупликация по
  «ссылка + озвучка»: дубляж и субтитры считаются разными просмотрами.
- **Сайты с плеером Kodik** поддерживаются автоматически — отдельный
  список доменов не нужен: плеер узнаётся в разметке страницы.
- **YummyAnime** — через открытый `/api/anime/<id>/videos`.
- **Подсказка об отказе не исчезает.** Раньше опрос пульта каждые 800 мс
  перезаписывал её словами «играет 0:00 / 0:00», и человек не успевал
  прочитать. Теперь отказ держится, пока не откроют другое видео или не
  закроют его крестиком, и сопровождается отдельной строкой «что делать».

## Плеер в игре

Переписан на v2. Кнопки на странице плеера, потому что в CEF внутри GTA 5
нет ни клавиатуры, ни браузерных средств:

- пауза/продолжить, «−10 с», «+10 с», звук, полный экран;
- полоса перемотки с буфером: тянется мышью, превью времени, буфер виден;
- ползунок громкости, иконка меняется при выключении звука;
- панель прячется сама через 2,5 с, но не уходит на паузе, под курсором
  и во время перетаскивания;
- клик по картинке — пауза;
- прямой эфир: полоса превращается в метку «ПРЯМОЙ ЭФИР», перемотка
  недоступна и говорит об этом;
- полный экран с запасным вариантом для CEF, где Fullscreen API нет.

## Звук

Нормализация громкости EBU R128. Раньше разброс между роликами достигал
19 дБ и приходилось крутить громкость на каждый; теперь 11 дБ.

## Пульт

- одна команда запуска: `python -m tvhost2.ui`;
- вкладки «Пульт», «Источники», «Журнал»;
- версия видна в заголовке окна — при разборе проблемы сразу понятно,
  какая сборка у человека.

## Проверки

- 702 теста собрано (в CI 672 проходят, 15 живых отсеяны), покрытие 68 %
  (порог в CI);
- ruff и mypy без замечаний, 60 модулей v2;
- в CI три задания: безопасность, линтер/типы/тесты, регресс на живых
  источниках;
- тесты на реальных ссылках заказчика;
- отдельно закреплены баги, которые иначе возвращаются молча: панель,
  которая рисуется но не нажимается (битый JS), и видео, перехватывающее
  клики у кнопок.

## Что осталось честно сказать

- **Серии у CVH выбираются «ближайшей меньшей».** Если просить 5-ю у
  тайтла из трёх, откроется 3-я, а не отказ: плеер не сообщает, сколько
  серий у каждой озвучки. У Kodik в такой ситуации честный отказ.
- **v1 в репозитории, но не в сборке.** Он остаётся для отката, тесты v1
  работают из исходников.

- **YouTube bot-check не обходим.** Часть ссылок не заиграет, плеер скажет
  об этом прямо.
- **hdrezka не поддерживается** — по решению заказчика.
- Память под нагрузкой замерена не была: цифры не выдумываю.
